Known trade-offs ​

Interceptor writer ​

  • It only sees SaveChanges. ExecuteUpdate, ExecuteDelete, raw SQL and other processes write no history. The trigger writer records them. See Interceptor writer.
  • Your own SaveChangesInterceptor runs after Hindsight's. A change it makes inside SavingChanges reaches the table without a version. Details.
  • Deleting costs one extra round trip: the row is re-read by key (SELECT … FOR UPDATE) so the tombstone holds real values. If the row is already gone, the save throws.
  • A failed history write leaves deleted entities detached. The transaction rolls back correctly, and Added / Modified entities are restored for a retry, but a Deleted one must be queried and removed again. Details.
  • A retried save of a restored Added entity with a store-generated key sends the key it received in the rolled-back transaction. With GENERATED BY DEFAULT AS IDENTITY (Npgsql's default) the retry succeeds and reuses that id. With GENERATED ALWAYS AS IDENTITY (UseIdentityAlwaysColumn()) PostgreSQL rejects it with error 428C9 until you reset the key property to 0.

Both writers ​

  • Bulk writes have no change context. Under the trigger writer, ExecuteUpdate, ExecuteDelete and raw SQL are recorded with NULL change-context columns.
  • The writers differ in two observable ways: the source of timestamps (TimeProvider or now()), and whether an update that sets a column to its current value writes a version. See Choosing a history writer.
  • The change context is asserted by the application, not guaranteed by the database. See the trust model.
  • EnableRetryOnFailure() needs your own transaction around a save that Hindsight would otherwise wrap in one. See Transactions.
  • Pooled and factory-created contexts need a singleton change-context provider. See Change context.
