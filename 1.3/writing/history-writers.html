Choosing a history writer ​

A history writer turns every insert, update and delete of a temporal entity into rows in its history table. Hindsight has two. Both produce the same history table and the same half-open periods, so you can switch between them with one migration.

Recommendation: HistoryWriter.Trigger

Use the trigger writer in production. It records every change, including ExecuteUpdate, ExecuteDelete, raw SQL and other processes, and it has no clock-skew exposure. Use the interceptor writer only if the role that applies migrations cannot create functions and triggers.

cs
services.AddDbContext<AppDbContext>(options => options
    .UseNpgsql(connectionString)
    .UseHindsight(hindsight => hindsight.UseHistoryWriter(HistoryWriter.Trigger)));

UseHindsight() without UseHistoryWriter(...) uses HistoryWriter.Interceptor.

Differences you can observe ​

Code that runs under both writers can tell them apart in two ways:

  • Timestamps. The interceptor uses your TimeProvider, so a test can inject time. The trigger uses now().
  • No-op updates. If EF Core marks a property as modified but its value did not change, the interceptor writes a version and the trigger does not, because the trigger compares the old and new row.

Switching writers ​

Change the option and add a migration:

bash
dotnet ef migrations add SwitchToTriggerWriter

The migration creates the trigger function and trigger (or, when switching back, drops them). It never touches your data or the history table's columns.
