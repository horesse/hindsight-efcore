# History writers

Hindsight can write history rows from two places. Both use the same history schema and the same
change context; you can switch between them with a migration.

| | `HistoryWriter.Interceptor` | `HistoryWriter.Trigger` |
|---|---|---|
| Where history is written | `SaveChangesInterceptor` in the application | plpgsql trigger generated by the migration |
| Catches `ExecuteUpdate` / `ExecuteDelete` / raw SQL / other services | no | yes |
| Timestamp | `TimeProvider`, one per `SaveChanges` | `now()`, one per transaction |
| Two app instances with clock skew | can produce overlapping intervals | safe: `GREATEST(now(), prev.valid_from + 1µs)` |
| Same transaction as the data change | yes | yes, by construction |
| Superuser or extension required | no | no — trigger functions need only table ownership |

## Recommendation

Use **Trigger** in production. It is the only mode that cannot miss a change.

Use **Interceptor** when your database policy forbids trigger functions, or when you want to see how
the application-side approach behaves. It is also the reference implementation the trigger is tested
against: the integration suite runs every scenario in both modes.

## How the change context reaches the trigger

At the start of each transaction Hindsight runs

```sql
SELECT set_config('hindsight.user_id', @userId, true),
       set_config('hindsight.correlation_id', @correlationId, true),
       ...
```

The third argument makes the setting transaction-local. The trigger reads it with
`current_setting('hindsight.user_id', true)`. Cost: one extra round-trip per transaction; the
benchmarks in the repository show the effect on single-row and batched saves.
